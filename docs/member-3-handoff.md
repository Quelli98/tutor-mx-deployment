# Sprint 1 Member 3 handoff

## Integrated scope

### S1-M3-1 - Tutor dashboard shell

- The Tutor role entry route opens `TutorDashboard` at `/tutor` through Member 1's protected role router.
- The dashboard calls `GET /api/tutor/dashboard` through the shared Auth0 bearer helper.
- The route has no tutor-ID path parameter. The Express backend derives the tutor from the verified Auth0 subject and checks the linked database role.
- The safe response contains only the current tutor's proposed/confirmed allocations plus the Member 6 weekly-hour summary.
- Filled, empty, loading, safe error and working retry states are implemented and tested.
- A newly onboarded Tutor with no organiser-configured weekly-hour limit now receives a valid empty dashboard instead of `TUTOR_HOUR_LIMIT_MISSING`; `weeklyLimit` and `remainingHours` are `null` until configured.
- Course/session, date/time, expected hours, allocation status and remaining weekly hours are visible.
- A request to `/api/tutor/dashboard/:tutorId` is deliberately not implemented and returns the shared `404` response.

Dashboard response shape:

```json
{
  "data": {
    "dashboard": {
      "allocations": [
        {
          "id": 4,
          "courseCode": "DEMO101",
          "courseName": "Demo Course",
          "startsAt": "2030-09-04T14:00:00.000Z",
          "endsAt": "2030-09-04T16:00:00.000Z",
          "allocatedHours": 2,
          "status": "CONFIRMED"
        }
      ],
      "weeklyLimit": 10,
      "usedHours": 6,
      "remainingHours": 4
    }
  }
}
```

The frontend validates this contract and rejects an unexpected or identity-bearing response instead of rendering it. For a valid new Tutor whose weekly limit has not been configured yet, the same response uses `"weeklyLimit": null` and `"remainingHours": null` while keeping `usedHours` numeric.

### S1-M3-2 - Availability, work-log and excuse forms

The Tutor navigation exposes `/tutor/forms`. It first loads the current tutor's safe dashboard projection, then supplies only confirmed own sessions to the forms.

#### Availability

- `POST /api/tutor/time-slots`
- Accepts `AVAILABLE` or `BUSY`, timezone-qualified ISO start/end values and optional `WEEKLY` recurrence.
- Invalid/missing dates, reversed ranges and unsupported recurrence are rejected before persistence.
- The new versioned migration adds the optional recurrence placeholder with a database check that permits only `WEEKLY` or `NULL`.

```json
{
  "type": "BUSY",
  "startsAt": "2030-09-04T14:00:00.000Z",
  "endsAt": "2030-09-04T16:00:00.000Z",
  "recurrence": "WEEKLY"
}
```

#### Draft work log

- `POST /api/tutor/work-logs`
- Requires an own confirmed allocation, its matching date, hours greater than zero and at most 24, and a non-blank description.
- The backend creates/reuses the tutor's Monday-starting draft timesheet in a Prisma transaction and attaches the work log.
- Cross-tutor allocations return `404`; locked timesheets, duplicate logs and database-rule conflicts return safe `409` errors.
- The UI shows the saved date, selected session and hours in the draft list.

```json
{
  "allocationId": 4,
  "workDate": "2030-09-04",
  "hours": 2,
  "description": "Tutorial session"
}
```

#### Excuse

- `POST /api/tutor/excuses`
- Requires an own future confirmed allocation and a non-blank reason.
- The database-owned initial state remains `PENDING`.
- Cross-tutor/past sessions return the non-revealing `404`; duplicates and rule conflicts return safe `409` errors.

```json
{
  "allocationId": 4,
  "reason": "Sick"
}
```

Every input is labelled. Field errors use `aria-describedby` and `aria-invalid`; invalid forms do not call the API.

## Security and integration boundary

- The browser sends `Authorization: Bearer <access-token>` through `src/api/client.js`.
- The browser never sends a tutor ID, imports Prisma, runs SQL or receives `DATABASE_URL`.
- Express resolves `Profile.auth0Id` from the verified token subject, requires the `TUTOR` role and applies ownership in every dashboard/form persistence function.
- Unexpected errors use the shared safe envelope and do not expose database or token details.
- Member 5 owns the authenticated routes/validation/transactions; Member 6 owns the schema, migration and constraint layer; Member 1 owns the role entry and shared bearer contract.
